## LMDI

```
net_revenue = sessions * conversion_rate * average_order_value * net_realisation
```

Every factor is read from the S1 warehouse under identical filters, so the product telescopes exactly: `sessions x (orders/sessions) x (gross/orders) x (net/gross) = net`. Architecture Part 7.1 writes the fourth factor as `(1 - Refund Rate)` from S3 finance; that version closes to only ~95%. See ADR-018.

Tolerance: `max(1e-06, 1e-09 x max(|V0|, |V1|))` — a floating-point rounding budget, not a modelling allowance. A decomposition exceeding it raises `ConservationFailure`.

### Cross-source reconciliation (reported, not absorbed)

| Quantity | Class | S1 | Other | Difference |
|---|---|---:|---:|---:|
| sessions | population | 32,842.4573 | 32,006.0744 | -2.55% |
| refund / leakage rate | definition | 0.1352 | 0.0667 | -50.64% |

- **sessions** — S2 sits -2.55% against the warehouse. 3.5% of S2 rows carry an unknown region (VPN / opted-out clients, declared in the contract as known_null_columns), so a region-filtered S2 total loses them; the remainder is hourly instrumentation noise. The conversion ratio is unaffected because S2 scales sessions and orders together - only the level differs.
- **refund / leakage rate** — the S3 finance refund rate (0.0667) is a different quantity from warehouse leakage (0.1352): it excludes discounts, which are a material part of the gap between gross and net. Using (1 - S3 refund rate) as the fourth identity factor would leave discounts unexplained, so the identity uses the warehouse net realisation rate instead. See ADR-018.

## Adtributor

### Paper reproduction

`tests/test_adtributor.py` reproduces the NSDI '14 worked example (revenue 100 -> 50). Data centre X carries EP **0.940** but surprise **0.000** — it produced 94% of forecast revenue and kept exactly that share. Device type carries EP **0.980** and surprise **0.138**, and the selected elements are `{Mobile, Tablet}`, whose share collapsed from 25% each to 1%. A magnitude-ranking heuristic blames data centre X; this implementation does not, and a test asserts the strawman really would get it wrong.

### Project scenarios — contribution-only vs contribution + surprise

| Event | True dimension | Adtributor | Correct | True slice found | Contribution-only picks | Correct |
|---|---|---|:--:|:--:|---|:--:|
| E1 | region | region | yes | yes | region | yes |
| E2 | product_category | product_category | yes | yes | product_category | yes |
| E3 | region | region | yes | yes | product_category | NO |

Adtributor identifies the intended dimension on 3/3 events and the intended slice on 3/3.

**Surprise changes the answer on E3.** On E3 the movement is largest in `product_category`, so ranking by size of change alone picks that and is wrong; the share that actually shifted is `region`, which is what the ground truth records.

**It does not change the answer on E1, E2** — there the biggest mover is also the most surprising one, and both methods agree. This is worth stating plainly: the West event is the headline demo for the *pipeline*, but it is not the case that demonstrates why surprise is needed. Use E3 for that, or the NSDI '14 example above, where the difference is unambiguous.

Large-but-normal elements are held back by construction: an element keeping its share contributes zero surprise however large it is (data centre X, EP 0.94, surprise 0.00). Small cells are held back by the `T_EEP` floor — an element worth less than 10% of the movement cannot enter the candidate set, and a cell worth 0.2% of the total that doubles still barely moves its share. Both are pinned by tests.

## Robustness

- **Method** — moving-block bootstrap over event-window days
- **Block length** — 5 days (one seasonal cycle where the window holds three; blocks rather than single days because daily residuals are autocorrelated)
- **Resamples** — 300, seed 20260822 (fixed, so the number is reproducible)
- **Statistic** — the share of resamples in which the same (dimension, element) is re-selected as top driver
- **Thresholds** — STRONG >= 80% with consistent sign; WEAK >= 50%; else UNSTABLE

Not a Welch p-value: Stage 3 established that the event window is selected to maximise displacement, so a pre/post test on that window is a post-selection statistic and returns p < 0.001 on pure noise (ADR-017). Welch is still computed and carried as diagnostic metadata; it decides nothing.

**driver stability = 100%** (region=West) -> **STRONG**

EP across resamples: mean +1.133, p05 +1.013, p95 +1.272, sign consistency 100%.

*Caveat:* window is 15 days against a 7-day season, so blocks are 5 days and the bootstrap is coarse

## Limitations

- **No attribution accuracy metric.** Ground truth names the dimension and slice of each injected event, and those are checked. It does not label the correct ranking of every non-event slice, so no precision/recall figure is manufactured for attribution. Detection has one because detection's labels support it; attribution's do not.
- **The data is synthetic and the events were injected by us.** Adtributor finding the dimension we planted is a correctness check on the implementation, not evidence it will work on production data.
- **The bootstrap is coarse on short windows.** A 15-day event with 5-day blocks gives three blocks; the stability figure is meaningful as a three-way verdict, not as a confidence interval.
- **DiD assumes the control is untreated.** Controls are chosen by pre-period correlation among unflagged slices. If an event were genuinely market-wide, every candidate would be treated and the check would correctly return DiD near zero — but it cannot detect a control contaminated in a way the pre-period does not reveal.
- **Parallel-trend tolerance is a chosen constant** (2%/day drift, 5% minimum effect), not derived from the data. It is a screening heuristic, not a formal test.
- **`net_realisation` deviates from the architecture's stated fourth factor.** Deliberate, measured and recorded in ADR-018.
